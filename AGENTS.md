# Repository instructions

## Repository map

- `plugins/` contains the installable `code-flow`, `code-quality`, `local-guards`, and `usage-metrics` packages, plus `agy-agents` with the Antigravity agent forms for `code-flow`; it installs for Antigravity only and stays out of the marketplace. Keep package-specific changes in their package.
- `.claude-plugin/marketplace.json` lists the packages of the `phil0v` marketplace for Claude Code and Codex. Each entry must lead to the directory of its package and carry the version and description of that package.
- `package.json` makes the whole repository one Pi package. Its `pi.skills` patterns must cover every skill directory.
- `plugins/code-flow/roles/*.toml` are canonical role definitions edited by hand, `plugins/code-flow/standards/` holds the review standards (`code-design.md`, `code-style.md`, `golang.md`, `symfony.md`, `frontend.md`, `agent-config.md`, and `test-quality.md` are generated by `tools/sync-standards.py` from `plugins/code-quality`; do not edit them), and `plugins/code-flow/references/` holds the workflow references, with hand-written per-harness dispatch notes under `references/harnesses/<id>.md`. `plugins/code-flow/harnesses/` and `plugins/agy-agents/agents/` are generated output; do not edit them. After editing the roles or the code-quality sources of the standards, regenerate with `make sync` and include both source and generated files.
- `plugins/code-flow/tools/` holds the maintainer tools; `plugins/code-flow/scripts/` holds the runtime scripts.
- `skills/` holds the standalone `retro` and `review-fix` skills. Package skills stay in their packages.
- `docs/install.md` is the installation runbook.
- Root tests are in `tests/`; each plugin has its own `tests/`.

## Change and validation rules

- Read the nearest applicable `AGENTS.md` before changing files. Prefer the narrowest relevant source of truth; avoid copying shared guidance into package files.
- Run tests only for affected roots: `make test-root` for the root suite, `make test-package PACKAGE=<name>` for one package. `make check` runs every suite, ruff, the manifest and link checks, the agent-form sync check, and `claude plugin validate` when the CLI is installed.
- Use the newest available Python 3 interpreter for Python commands. Install test dependencies from the repository root with `python3 -m pip install -r requirements.txt` only when needed.
- Package runtime scripts must run on the system `python3` (3.9+): standard library only, or a vendored fallback committed inside the owning package (`tomllib` via each package's `_tomli`); never require a runtime pip install. Test capability skips cover optional test-only dependencies, not runtime script requirements.
- For script or hook changes, add or update focused tests. For generated files, run the package's generator (`make sync`) and include the output; `make sync-check` fails when it is stale.
- Every new test verifies observable behavior or a packaging interface: script and hook execution, manifests, frontmatter, symlink layout, generated artifacts, link resolution. Shipped prose is not a test surface: do not pin its wording, section inventory, or ordering, do not assert that a phrase is absent, do not assert the contents of other test files, and do not add fixtures read only by the test that asserts them. Check the affected root for existing coverage before adding a test and extend it rather than duplicate.
- After implementing a plan or change, delete tests that pin shipped prose (wording, section inventory, ordering, or phrase presence/absence), assert other test files' contents, or no longer verify current behavior. Delete fixtures used only by removed tests. Preserve tests of observable behavior, packaging interfaces, and safety invariants; CLI output and synthetic plan/task inputs consumed by scripts are behavior, not shipped prose.
- For documentation-only changes, verify referenced paths and links and review the rendered Markdown. For manifest changes, validate the affected JSON files.
- Keep documentation concise, in English, and use descriptive headings and language-tagged code fences. Use lowercase, hyphenated skill and directory names; preserve established filenames such as `SKILL.md` and `plugin.json`.
- Use ASD-STE100 (Simplified Technical English) for prose in skills, instruction files, and docs.
- Keep skills compact. Use short, direct instructions. State required steps, approvals, stop conditions, and exceptions in `SKILL.md`. For shared procedures, point to the exact reference section instead of repeating it. Remove repetition, not requirements.
- Always include `argument-hint` in the YAML frontmatter of every `SKILL.md`.
- Keep scripts portable. Do not add credentials, machine-specific paths, private data, or unrelated changes.

## Contribution conventions

- Keep each change focused. Use concise imperative commit subjects, optionally prefixed by scope.
- Describe user-facing or maintainer-facing behavior and validation in pull requests; link related issues when relevant.
