# Dispatch bundled workflow roles

## Package resources

Resolve this package root from the absolute filesystem path used to load the workflow `SKILL.md`: the file is under `skills/<skill>/SKILL.md`, so the package root is two directories above its containing skill directory. Resolve symlinks first. Every skill with a `## Package resources` section restates this resolution rule. The skill uses it to locate this reference before first resolution. Change the wording in both places together. Keep that root separate from the target repository and its working directory. If the loader provides only a resource URI, use its package-location metadata. If that location is unavailable, block before you use this reference.

Read this reference using that root. It defines bundled roles, review references, and capability preflight. Resolve sibling workflow skills by their package-local paths and follow those files directly, carrying flags and authorization. An unqualified skill name can select another installed copy.

All paths in bundled role instructions and review references beginning `<package>/` resolve against this root. Supply it to every agent. These TOML files are resources. The portable plugin manifest does not register native agent roles. `<package>/tools/sync-agents.py` generates the per-harness forms and declares their locations. Each harness note under `<package>/references/harnesses/<id>.md` names the forms of its harness, or states that the harness loads none. An on-disk form establishes the expected contract. Native dispatch requires evidence of the actual loaded profile.

The interpreter rule in `<package>/references/checks.md` extends to every package-script invocation these references prescribe. This includes the `role-profile.py`, `review-manifest.py`, `review-snapshot.py`, `style-gate.py`, and `run-check.py` scripts. Resolve that interpreter once per run; do not assume `python3` resolves to it. Name it in the dispatch prompt so no dispatched agent re-derives it.

Load each package resource once per conversation. If a reference is already loaded in this conversation, do not re-read it unless its file changed. A nested flow inherits the parent's loaded references. The parent's dispatch prompt of the nested close-out agent carries this note: `references already loaded in this conversation, unchanged since load: <paths>`. The nested flow's dispatch prose consumes that note. It does not re-list the reads. After a compaction resume, nothing counts as loaded. The flow reloads exactly the references it lists.

## Capability preflight

Before edits, identify the active harness and resolve each required role's effective profile as described below. Read the target repository's instructions. Installation grants no permission to edit personal roles, configuration, or the target project's instructions.

The bundled harness ids are those `role-profile.py --list-harnesses` reports. `agentic` is the generic profile; the resolver always accepts it. For an unlisted harness, resolve `agentic`. For a listed harness, read `<package>/references/harnesses/<id>.md` when it exists. It carries the native dispatch API, the role-to-profile mapping, the form location when the harness has forms, and the verification evidence where one exists. A note without evidence leaves its effort mechanism unverified under Model and effort routing. Without that file, the generic adapter rule in Role resources applies. Use runtime defaults only for model or effort that the request did not specify. If a listed harness cannot match its required native role, use a generic agent adapter. Give it that harness's resolved concrete model and effort for values the user did not specify. Do not replace them with the `agentic` profile. In either branch, dispatch is eligible only if the environment exposes a verified agent-delegation API. That API must start a fresh agent and select the required profile. It must apply canonical instructions and role-appropriate tools and return the complete result. Apply an explicitly requested model or effort instead of the resolved value if the API supports it. If a requested value cannot be applied, block dispatch. For the `agentic` profile, if no effort was requested, leave runtime effort unchanged. Verify that the effective profile is suitable for the role. Block dispatch if it cannot be selected or if any required capability is unavailable. Honor higher-priority dispatch constraints. If they prohibit this fallback, block dispatch. An unlisted generic Agent Skills reader must verify its actual API and profile before dispatch. Skill discovery and readable package resources alone do not establish execution support. A reader without an adapter must not assume the tool names of another harness.

## Effective profiles

Run the resolver as follows. The first command lists the accepted harness ids; the others resolve one role name or a comma-separated list of unique role names from the table:

```sh
python3 "<package>/scripts/role-profile.py" --list-harnesses
python3 "<package>/scripts/role-profile.py" --harness <harness> --role worker
python3 "<package>/scripts/role-profile.py" --harness <harness> --role worker,reviewer,style-reviewer
```

`--list-harnesses` takes no `--harness` or `--role`. It exits 0 and emits `{"harnesses": [<id>, ...]}` in lexical order. Replace `<harness>` with the active harness id. For an unlisted harness, resolve `agentic` to obtain the canonical instructions. For a single role, exit 0 emits a JSON object containing `name`, `description`, `model`, `effort`, `effort_policy`, canonical `developer_instructions`, and native `tools` when declared. For a comma-separated `--role` list, exit 0 resolves each role in one call in input order and emits `{"profiles": {<role>: <profile>, ...}}`. The resolver applies `--provider`, `--gate-report`, and `--round-kind` to each matching role in the batch. Empty or duplicate role names, unknown harnesses or roles, and malformed package mappings emit a JSON `error` and exit 2. Stop dispatch on failure.

An optional `--provider <id>` overrides the mapping's provider selection for that one resolution. It is never persisted into forms or state. The named provider table supplies the resolved model and, when an entry declares it, the effort. The `effort_policy`, tool lists, and instruction bodies stay role-owned. An unknown provider id or a mapping without `providers` fails with that same JSON `error` and exit 2. Provider selection never changes the routing rules. The `### Model and effort routing` conditionals still apply on top of the provider-resolved profile. The entry model and any entry effort come from the selected table. Native forms always render the mapping's own provider selection. Thus a dispatch resolved under a different provider cannot match native loaded-profile evidence. It follows the Capability preflight fallback: a generic agent adapter with the resolved concrete model and effort.

A harness with an entry in `<package>/harnesses/mapping.json` takes its model and effort policy from that entry. A harness without an entry takes them from the canonical role TOML. Instruction bodies always come from TOML. In an `agentic` profile, `model: "runtime-default"` and `effort_policy: "unsupported"` mark runtime-resolved values. They do not claim a selected model or effort. These markers are resolver metadata, not API arguments. `effort_policy: explicit` requires the non-null `effort` value. `effort_policy: unsupported` requires `effort: null`. Generated native forms omit that effort. A mapping entry can mark its roles with the runtime-default markers. The dispatch then leaves model and effort to the profile's settings resolution unless the request pinned them. A provider table can also supply concrete models. At dispatch, an explicitly requested effort takes precedence. Pass it only if the API supports it; otherwise block. When no effort was requested, omit the API effort argument for an unsupported profile and use the verified runtime default. Never pass a runtime marker as an API argument. Record the actual runtime profile in dispatch evidence. The generator consumes this same resolver.

### Model and effort routing

Role model and effort assignments route by the judgment content of the role's output:

- Where the harness pins a model and effort, `worker`, `reviewer`, `plan-reviewer`, and `spec-reviewer` use the strong model that the mapping or the role TOML resolves, at the resolved effort. A mapping can pin a lower `worker` effort for scoped implementation. The reviewer post-exit rule below applies on top.
- Mechanical execution — `tool-runner` — stays on the cheap model at low effort (see `<package>/roles/tool-runner.toml`). Its output is executed check evidence, not judgment.
- A native `reviewer` profile with `effort_policy: explicit` runs at `high` effort by default. If the user did not request an effort, a `reviewer` dispatch for a `post-exit-correctness` round resolves to `medium` effort on the same resolved model. `initial-correctness` and `targeted-correctness` dispatches keep high effort.
- A native `style-reviewer` profile with `effort_policy: explicit` runs at `medium` effort by default. It runs at `low` effort only on dispatches that carry a verified style-gate report. The pre-dispatch gate contract in `<package>/references/closeout.md` defines that report. Apply this gate preference only if the user did not request an effort. It never changes an agentic runtime default.

This section is the single authoritative source for native-profile routing values. This includes the conditionals' values: style-reviewer default `medium`, gated `low`; reviewer default `high`, post-exit `medium`. Each preference applies only to native profiles whose policy is `explicit`. It applies only if the user did not request an effort. Neither conditional changes an agentic runtime default or the resolved model. Role instructions and the resolver reference this rule rather than restating its rationale. Changing any role's model or effort requires an update to this rule in the same change. The routing rationale lives in exactly this one place.

Each harness note names where effort is carried — a form key, an API argument, or nothing — and the evidence that verified that mechanism, when evidence exists. The evidence verifies the schema and adapter mechanism, not a live run or provider support for each model. Check the installed extension and model capability before dispatch. An unavailable selected effort is a blocker. Treat another harness or extension version's effort mechanism as unverified until its schema and launch path are checked.

For each dispatch, use the resolver's effective profile. The table indexes canonical instruction resources. It does not override harness model mappings. A configured native role is usable only under one condition. Its actual loaded-profile evidence must match the resolved model, supported effort, declared tools, and complete instruction body. Only leading/trailing newline normalization of the body is allowed. Inspect runtime registry or launch metadata for overrides as well as the role definition. A shared name, generated file on disk, or installation path alone is insufficient. If native-role evidence is insufficient, follow Capability preflight for fallback eligibility.

When the selected profile requires a generic agent, create a fresh one. Use the profile selected under Capability preflight. For a listed harness fallback, use that harness's resolved concrete model and effort. For an unlisted harness, use the `agentic` profile and leave unrequested runtime defaults unchanged. Never pass `runtime-default` or a null marker as a model or effort API argument. Omit the corresponding argument and record the actual effective runtime profile. Launch through the API the harness note names, or through the API verified under Capability preflight when no note exists, with a generic agent type rather than an unverified personal role.

Delegated agents may receive a replica or copy of the target checkout. An isolated replica can lag the live worktree. Thus an inspector dispatched for a review or verification round must judge the repository of record. It reads its assigned files there directly. It consumes the round's pre-executed diff artifact as the diff source instead of re-deriving the diff from the replica. If the harness cannot share the live checkout, the dispatch states both requirements explicitly. An inspector that cannot read the repository of record returns that blocker instead of findings. A verdict reported from replica content is an incomplete return under the coverage gate. It is not a completed inspection, even when its artifact hash verifies.

The dispatch prompt names the repository of record (the path the coordinator reads). It requires the agent to confirm read-only, before reporting completion, that its assigned edits are visible there. For tracked files, staged and unstaged alike, it runs `git -C <repository-of-record> diff HEAD -- <assigned paths>`. It also runs `git -C <repository-of-record> status --porcelain -- <assigned paths>` with each untracked file's SHA-256. Thus a newly added path is never reported as invisible. An agent that shares the coordinator's checkout performs this direct confirmation itself. An agent whose edits land in a replica or isolated copy cannot perform it. That agent completes by reporting its edits as unmerged changes, with the post-edit SHA-256 of every changed file. The coordinator then merges and hash-verifies them.

The dispatch prompt carries the profile's canonical `developer_instructions` by reference. That reference is the absolute path to the role TOML under `<package>/roles/` plus the SHA-256 of its current content. The agent reads the `developer_instructions` body from that file before starting. A hash mismatch at read time blocks the dispatch unless git corroborates the file. If the repository of record is clean at HEAD, compare the file's actual SHA-256 with the blob hash of `git -C <repository-of-record> show HEAD:<path>`. If they are equal, the quoted value was stale dispatcher metadata. The agent then proceeds under the git-canonical content and reports the stale value as a dispatcher deviation. An uncorroborated mismatch still blocks. Examples are a dirty tree, a missing path, or a differing blob. The reference is followed by:

- the absolute package root and the rule resolving `<package>/` paths against it;
- the target repository root and explicit assigned file ownership;
- the repository of record path. The agent must confirm that its assigned edits, tracked and untracked alike, are visible there before reporting;
- the user's request, approved step, or finding as supplied, with existing pointers, requirements, constraints, and acceptance baseline;
- that every task that names a check carries the exact check argv (the exact-check-argv rule), which the coordinator will verify. It is never a paraphrase that the dispatched agent must reconstruct into a runnable command. The argv is in its non-interactive form — stdin closed, no TTY prompt — so the dispatched agent never invents the transformation. The dispatched role can be unable to execute a check or gate that the coordinator will apply. Examples are an isolated checkout without Docker, or a missing linter or formatter binary. In that case, the dispatch constraints state its mechanical counting rules or an explicit margin. One margin is staying at least one below the configured limit. This replaces leaving the worker to estimate;
- the resolved harness value with the exact resolver argv. That argv carries the resolved interpreter, the `--harness` value for the active harness, and the role. It carries the applicable `--round-kind` or `--gate-report` and `--repo` flags. It carries the applicable `--provider` when the dispatch resolves a provider table. Thus a dispatched agent consumes the resolved routing from its prompt. It does not re-run the resolver with its own harness name;
- for inspectors, the validated review-round manifest path and the assigned group ID under Review-round manifests below. If the harness cannot share the file, carry the complete rendered group packet instead. On the single-group no-manifest fast path owned by `<package>/references/closeout.md` Run step 1, carry that step's inline inputs instead. Those inputs are the assigned files and complete scoped file list, the exact diff command, scoped untracked files, constraint paths, and the acceptance checklist. For reviewers, the chosen review reference;
- that the agent is not alone in the repository and must preserve other edits.

A context-pack path supplied with a dispatch or through a review manifest is advisory. It accelerates orientation and never substitutes for the reading a role owes.

The initial correctness round dispatches one fused inspector per group under the round rule owned by `<package>/references/closeout.md` Run step 1. That dispatch uses the `reviewer` profile with `initial-correctness`. Thus the model and effort routing above applies unchanged. The final round dispatches its fused inspectors under the same profile and the round rule owned by `<package>/references/closeout.md` Run step 4. The `style-reviewer` profile remains the routing target for a style-only dispatch that a workflow explicitly orders.

The main agent owns routing, coverage/acceptance gates, checks, and commit authorization. A worker works within its scope directly and leaves recursive dispatch and close-out to the caller. Inspectors remain independent and read-only. Pass blockers to the caller. A missing tool or incomplete return is not success. A failed agent may still return mergeable-looking partial output. Partial changes from a failed agent are never merged. Discard follows the landing mode. Results reported as unmerged changes are dropped unapplied. Edits already applied in a shared checkout are reverted against the assigned paths' SHA-256, captured before the dispatch. The coordinator then redispatches the complete task fresh. Provider quota or rate-limit failures are reported as infrastructure blockers rather than task failures.

## Evidence by reference

An artifact exchanged with a dispatched agent — dispatch input or agent return — that exceeds the bound never travels inline. The bound is a short summary, on the order of a dozen lines. A larger artifact lives in a repository-external or temporary file. A reference to it names its path, the SHA-256 of its content, and a bounded summary. The summary states what the artifact establishes. The location must be durable. It outlives the producing turn or terminal invocation and stays readable by the receiving agent. Never use a thread-local scratch directory. Before relying on the artifact, the receiver recomputes the hash from the referenced file and compares it. A mismatch, a missing file, or an unreadable file is unavailable evidence. It blocks the use it was meant to support. This covers handbacks, check logs, diffs, manifests, coverage lists, and finding evidence excerpts.

Findings themselves stay inline. Identifier, file:line, severity and cost, and suggested replacement are the payload of a review result. They are not evidence bulk and are never moved into a referenced file.

## Review-round manifests

When the calling workflow dispatches a review round from a manifest, it writes the manifest to a temporary file outside the repository worktree. It validates the manifest with `python3 "<package>/scripts/review-manifest.py" validate --repo "<repository>" --manifest <path>` before any inspector dispatch. Review-round dispatch concurrency follows the wave rule owned by `<package>/references/closeout.md` Run step 1. That step fixes the wave size and the retain-and-retry fallback. It also gates close per round rather than per wave. This reference sets no separate review-round concurrency cap. Dispatching the round's inspectors means dispatching them under that rule.

Each inspector prompt still carries the user's request, approved step or finding. It carries the chosen review reference, constraints, authorization, model, and effort. It carries the canonical developer instructions by reference under Role resources. That reference is the role TOML's absolute path plus the SHA-256 of its current content. The manifest supplies the complete original and current scope, group ownership, exact diff commands, scoped untracked files, and constraint paths. It also supplies the acceptance routing appropriate to the round kind. Each inspector loads and validates the manifest and renders its named group before reading. If a harness cannot share the temporary file, render the group packet with `render --manifest <path> --group <id>`. Include the complete packet inline. Validate the inline packet by re-running `render` and comparing byte-for-byte before dispatch. A missing, unreadable, invalid, or mismatched manifest or packet blocks the dispatch. No one guesses a scope. Only the coordinating workflow writes or rewrites a manifest. If a fix needs another path, the worker reports the path and its reason. The coordinator then regenerates and revalidates the manifest before the next dispatch. Remove the manifest after its round.

The scope invariants are owned by `review-manifest.py validate`, the only form inspectors run, as their single source. It enforces the `round_scope`, `added_paths`, and `scoped_untracked` containment rules. It also enforces the `excluded` invariants. An `excluded` path stays within `original_scope` and out of `round_scope` and `scoped_untracked`. No `added_paths` entry is also excluded. When a fix round leads to another, carry prior rounds' added paths into the next manifest's `original_scope`. Alternatively, keep them as `added_paths` again. Never silently drop them. The common failure mode is building `original_scope` as "previous original plus new files" while also listing the new files as `added_paths`. That double-counts them and fails validation.
